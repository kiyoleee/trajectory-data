## Goal

Write a single-file Python 3 script `poc.py` that drives the provided target
binary through one deterministic multi-user scenario and emits a fixed JSON
result. The script is executed by an external evaluation harness that only
provides the binary path.

## Target binary

- The caller passes the target binary with `--binary <path>`.
- The target is a privileged, sudo-like command-line tool that manages
  per-user privilege rules through a root-owned configuration file.
- The tool requires effective root privileges; its standard installation uses
  the setuid-root mechanism so an unprivileged account can invoke it with
  elevated rights.
- The tool reads its configuration from `/etc/sudoers-rs` when that file
  exists, otherwise from `/etc/sudoers`.
- The tool'"'"'s standard interface includes a privilege-listing mode (`-l`) and a
  user-selection option (`-U`) used to target another account.

## Scenario

Your script runs as root in a fresh, network-isolated Linux container. During
the run it must dynamically construct the whole scenario:

1. Create two unprivileged accounts named exactly `invoker` and `victim`
   (for example with `useradd -m`); reuse them if they already exist.
2. Write the tool'"'"'s configuration file `/etc/sudoers-rs` (owned by root, mode
   `0440`) with exactly this content:

   ```
   invoker ALL=(ALL:ALL) NOPASSWD: /bin/true
   victim ALL=(ALL:ALL) ALL
   ```
3. Make sure the tool'"'"'s PAM service entry exists at `/etc/pam.d/sudo`. Use
   a comment-only service file (no module lines), and neutralize the fallback
   files `/etc/pam.d/other` and `/etc/pam.conf` the same way: the tool'"'"'s PAM
   bootstrap must succeed without loading any shared PAM module in this
   container.
4. Install the target binary so an unprivileged account can invoke it with the
   standard setuid-root mechanism: copy it to a private location, make it
   owned by root, and set mode `4755`.
5. Acting as `invoker`, invoke the tool in its privilege-listing mode while
   selecting `victim` as the subject, with no command argument:
   `<installed-tool> -l -U victim`
6. Capture the complete standard output and standard error of that invocation.

## Required interface

- `--binary <path>` (required): path to the target binary.
- `--json-out <path>` (optional): mirror the JSON result to this file if given.
- `--timeout <seconds>` (optional): per-invocation timeout.

## Required JSON contract

Print exactly one JSON object to stdout with these fixed keys:

- `binary`: string, the `--binary` value
- `command`: list of strings, the exact command executed
- `returncode`: int or null
- `signal`: string or null
- `timed_out`: boolean
- `runtime_ms`: integer
- `stdout`: string
- `stderr`: string
- `observable`: object with `kind`, `value`, `path`; the normalized
  evaluator-facing evidence. Set `kind` to the output kind and put the full
  combined invocation output in `value`.
- `error`: string or null

## Rules

- The script must build the trigger scenario dynamically during each run. It
  must not read a prebuilt payload or scenario file from any fixed absolute or
  relative path, and it must not require extra payload-path arguments.
- The script must be self-contained, idempotent (repeated runs must succeed),
  deterministic, and bounded: no unbounded fuzzing, no interactive prompts,
  and no network access.
- Do not hard-code host-specific paths beyond the fixed system paths listed
  above.
